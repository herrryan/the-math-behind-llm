# 概念 27 - 永不停歇的过山车站台：连续批处理（Continuous Batching）与插队顺风车

---

## 老师引言：为什么传统批处理在推理服务里是极大的灾难？

在深度学习的课本上，我们被灌输了一个神圣的原则：**批处理（Batching）越大越好**！
把 64 个或者 128 个样本打包在一起塞给显卡，显卡的吞吐效率最高。
在模型“训练”时，这个原则颠扑不破；
然而，当工程师把这套“打包批处理”原封不动搬到生产环境的**在线推理对话服务**时，却引发了一场灾难性的排队海啸。

为什么同一个打包思维，在训练时是神器，在服务时却成了毒药？
这背后就是大模型从“静态死板批处理”走向“生命细胞级连续批处理”的伟大进化。

---

## 生活实体模型：游乐园过山车的两种运营模式

想象游乐园里有一辆四座的超级过山车：
队列里排着四位游客：
- 游客 A：只想体验 10 秒钟；
- 游客 B：想玩 30 秒；
- 游客 C：想玩 1 分钟；
- 游客 D：买了一张连续玩 50 分钟马拉松的终身套票！

### 1. 传统静态批处理（Static Batching）：荒唐的陪跑地狱
传统的批处理就像一个极其教条刻板的过山车检票员：
四个人同时系好安全带，过山车出发。
10 秒钟后，游客 A 已经玩够了，脸色发白想要下车。
但检票员死死把安全压杠锁住：“不行！我们是一个批次！必须等游客 D 把 50 分钟彻底坐完，所有人才能一起下车！”
于是：
- 游客 A 在座位上干坐了 49 分钟又 50 秒的无聊冷板凳；
- 围栏外，排着长龙的上百位游客在烈日下焦急张望，但检票员坚决不准任何人入场！
在这 50 分钟里，整辆车有三个座位长期坐着无所事事的“空人”，**高达 70% 的运力被凭空浪费了**。这在计算机系统里被称为**计算气泡（Bubble Waste）**。

### 2. 连续批处理（Continuous Batching）：永不熄火的流水线
聪明的游乐园换了一位天才调度员：
过山车在轨道上疾驰，但每飞驰一圈经过站台时，只轻巧减速 1 秒钟：
- 谁玩够了，咔哒一声解开安全带走下站台；
- 队列最前面的新游客立刻一个健步跳上空出来的座位，扣紧卡扣；
- 过山车呼啸着重新冲向轨道——**每一个座位在每一圈都被坐得满满当当！**

```
┌────────────────────────────────────────────────────────────────────────┐
│                        静态批处理 VS. 连续批处理                       │
├────────────────────────────────────────────────────────────────────────┤
│ 静态批处理 (粗粒度请求级):                                             │
│   槽位 0: [ 短请求 A (3字) ] ──► [ 空转等待... 空转等待... 空转等待... ] │
│   槽位 1: [ 长请求 B (50字) ─────────────────────────────────────────] │
│   ──► 槽位 0 必须全程陪跑！新请求全被堵在门外！                        │
├────────────────────────────────────────────────────────────────────────┤
│ 连续批处理 (细粒度单字迭代级):                                         │
│   槽位 0: [ 短请求 A (3字) ] ──► 结束下车 ──► [ 新请求 C 立即上车接替 ] │
│   槽位 1: [ 长请求 B (继续生成第4字...) ─────────────────────────────] │
│   ──► 槽位永不空转，气泡彻底归零，系统吞吐量翻倍暴涨！                 │
└────────────────────────────────────────────────────────────────────────┘
```

## 它在大模型里到底怎么工作？

在大模型推理系统里，这一机制被称为 **连续批处理（Continuous Batching，由微软与首尔大学团队在 Orca 系统中首创）**。
它的调度时钟不再是“整篇对话”，而是细致到了**“每生成一个词元的离散瞬间”**：
在每一个前向步完成的毫秒瞬间，系统都会检查哪位用户输出了终止符 `<eos>`。一旦有人完成，他的槽位立刻被腾空，等待队列里的新请求在下一毫秒无缝插槽！

### 分块预填（Chunked Prefill）：巧妙搭上顺风车
但这里还有一个隐藏的痛点：如果新来的请求带着一篇 8000 字的超长论文（Prefill），它一旦插队进来，会不会把正在流畅打字的人全给卡停好几百毫秒？
答案是用 **分块预填（Chunked Prefill）**：
把这 8000 字切成每块 512 字的小包裹，每一圈让大象搬一个包裹上车。
更绝妙的是，原本深陷显存读取瓶颈的解码词元，**顺便蹭上了超长文档搬运权重的顺风车**！解码延迟不仅不增加，显存带宽还被榨取得淋漓尽致。

## 如果拿掉它，世界会怎样？

如果没有连续批处理：
- 现在的任何大模型商业 API（如 OpenAI 或国产各类 API）其服务器成本至少要翻三倍，因为大部分算力都在为短请求填充无效的空白 Padding；
- 用户端会遭遇极其严重的延迟抖动——有时秒回，有时因为排在别人长请求后面而莫名其妙被卡住几十秒。

## 老师划重点

!!! tip "核心心法"
    **连续批处理打破了整篇请求的时间枷锁，将调度粒度精细到了每一个词元跳动的刹那。随到随走、有空即补的细胞级运转，彻底挤干了显存气泡的最后一滴水分。**
