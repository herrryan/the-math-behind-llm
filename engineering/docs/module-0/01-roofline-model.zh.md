# 第 E01 章：屋顶模型推导与算术强度：计算密集型 vs 访存密集型工况判定

同学，你好！在上一章里，我们推导出了一个令人震惊的事实：如果算法设计不当，GPU 99% 的时间可能都在等数据运过来。

今天这节课，老师要教你一套在整个高性能计算和 AI 基础设施界无往不利的“照妖镜”——**屋顶模型（Roofline Model）**。

学会了它，以后面对任何一个运行缓慢的大模型代码，你只需掏出草稿纸算两分钟，就能一眼看穿它的物理病根到底在哪里！

---

## 步骤 1：物理直觉（果汁摊里的破壁机与搬运工）

为了让你彻底搞懂，老师给你讲一个校门口鲜榨果汁摊的生动故事：

你的果汁摊上有两位搭档：
1. **备料搬运工（显存带宽）：** 负责从后面的仓库搬来大箱的冻草莓和纯净水。他手脚再快，**每分钟最多也只能拆箱倒进 3 公斤原材料**。
2. **大功率超高速破壁机（Tensor Core 算力）：** 一台工业级搅拌机，刀头转速极高，**每分钟能疯狂旋转 3,000 圈**。

现在，店里来了两位截然不同的顾客：

- **第一位顾客点了一杯“清爽草莓水”：**  
  配方很简单：倒满 1 升纯净水，扔进 1 颗小草莓，破壁机轻轻转动 2 圈搅拌均匀即可出杯。  
  搬运工为了搬来沉重的大桶水，气喘吁吁忙活了整整 20 秒；而破壁机“嗡”了一声，只转了 0.1 秒就停下了。在剩下的 19.9 秒里，昂贵的大功率破壁机完全闲置，只能干等着搬运工去搬下一桶水。  
  此时，果汁摊的产能完全被搬运工卡死，这在计算机体系结构中叫做**访存密集型（Memory-Bound，搬运受限）**。

- **第二位顾客点了一碗“极致浓缩草莓冻霜”：**  
  配方截然相反：不需要加水，只要搬来一小碗草莓，但要求破壁机以最高转速疯狂研磨 30 秒，打碎到微米级极度细腻的糊状。  
  搬运工花 1 秒钟把一小碗草莓倒进杯子后，就可以在旁边翘着二郎腿喝茶了；而破壁机必须开足全马力轰鸣整整半分钟！  
  此时，果汁摊的产能完全被破壁机的机械功率卡死，这叫做**计算密集型（Compute-Bound，算力受限）**。

你看，**破壁机到底转了多少圈（FLOPs 做功次数），除以搬运工到底扛了多少斤食材（Bytes 搬运字节数），这个比值就叫做“算术强度”！**

## 步骤 2：芯片微观底层执行机制

在计算机硬件中，加州大学伯克利分校的图灵奖得主 David Patterson 教授等人将这一物理现象抽象为了著名的**屋顶模型二维坐标图**：

```
真实达到的算力 [TFLOPS]
         ▲
峰值     │                          /────────────────────────── (算力天花板: P_peak)
算力     │                         /
天花板   │                        /
         │                       /
         │                      / ◄── 显存带宽斜坡天花板
         │                     /      斜率 = 硬件显存带宽 (BW_mem)
         │                    /
         │                   /
         │                  /
         │                 / │
         └───────────────┴───┴───────────────────────────────► 算术强度 I
                         0   I* (硬件平衡临界拐点)                 [FLOPs / Byte]
                          ▲
                          │
          [访存受限区间]  │   [计算受限区间]
          I < I*          │   I > I*
          (显存总线跑满,  │   (Tensor Core 跑满,
           算力单元挨饿)  │    显存带宽充裕)
```

### 老师带你细读坐标轴的每一个参数：

1. **纵轴：实际达到的计算吞吐（Performance）：**  
   单位是 $\text{TFLOPS}$（每秒万亿次浮点运算）。纵轴最高有一根平平的“天花板”，这就是芯片的**物理峰值算力 $P_{\text{peak}}$**（无论你的代码写得多好，都不可能越过硬件的理论天花板）。
2. **横轴：算术强度（Operational Intensity，符号为 $I$）：**  
   单位是 $\text{FLOPs / Byte}$。它衡量你的算法**每从显存里艰难搬来 1 个字节的数据，能够在芯片里对它反复蹂躏、计算多少次**！
3. **左侧倾斜的斜坡（斜率即物理带宽 $\text{BW}_{\text{mem}}$）：**  
   如果你的算术强度很低（在左侧），你根本够不着上方的平顶天花板，你只能撞在左边的斜坡上！因为此时显存总线已经堵死了，算力再高也使不出来。
4. **屋檐转折点（硬件平衡拐点 $I^*$）：**  
   两个天花板相交的那一个交点，是整张图的核心灵魂！
   $$I^* = \frac{P_{\text{peak}}}{\text{BW}_{\text{mem}}}$$

## 步骤 3：跨组件相互耦合机制

理解了屋顶模型，你就能一眼看懂大模型中两个截然不同的核心阶段：

1. **提示词预填阶段（Prefill 阶段）：**  
   当用户把一大段长达 2000 字的提示词喂给大模型时，模型要把这 2000 个 Token 的大矩阵与权重矩阵相乘。此时矩阵尺寸极大，算术强度极高（$I \gg I^*$），直接落入**计算密集型区间**！这一阶段，Tensor Core 满负荷轰鸣，芯片发热量飙升，系统瓶颈在于算力是否充沛。
2. **逐字吐字生成阶段（Decode 阶段）：**  
   大模型自回归生成时，每次只能蹦出 1 个新词（批大小为 1 时，输入矩阵行数 $M = 1$）。为了生成这单个 Token，GPU 必须把整整 700 亿个参数从冷库 HBM 完完整整读取一遍，但每个参数只做了一次乘法！算术强度低到了可怜的 $I \approx 1\text{ FLOP/Byte}$，深陷在**极度访存受限区间**！此时 Tensor Core 几乎全程都在睡觉打呼噜。

---

## 步骤 4：精确性能数学公式

任何算法在硬件上能达到的理论最高性能上限 $P$，可以用一个极简的数学公式统领：

$$P = \min\left(P_{\text{peak}}, \; I \times \text{BW}_{\text{mem}}\right)$$

执行该任务所需的理论最短物理时间为：

$$T_{\text{min}} = \max\left( \frac{\text{FLOPs}}{P_{\text{peak}}}, \; \frac{\text{Bytes}}{\text{BW}_{\text{mem}}} \right)$$

## 步骤 5：具体微基准数字推导

来，拿出笔，跟老师一起在现代主流芯片上算一下这个神秘的临界点 $I^*$！

以 **NVIDIA H100 SXM** 芯片为例：
- BF16/FP16 密集峰值算力：$P_{\text{peak}} \approx 1,000 \text{ TFLOPS} = 1.0 \times 10^{15} \text{ FLOPs/s}$
- HBM3 物理显存带宽：$\text{BW}_{\text{mem}} \approx 3.35 \text{ TB/s} = 3.35 \times 10^{12} \text{ Bytes/s}$

### 1. 计算硬件平衡拐点 $I^*$
$$I^* = \frac{1.0 \times 10^{15}}{3.35 \times 10^{12}} \approx 298.5 \text{ FLOPs/Byte}$$

**老师敲黑板划重点：**  
这个数字 $298.5$ 意味着什么？  
它意味着在 H100 上，**你每从显存里搬运 1 个字节（半个 FP16 数字），必须在芯片里对它反复运算整整 298 次，才能让显卡发挥出它宣传的 1000 TFLOPS 峰值！**

### 2. 算一算自回归生成（Decode）的尴尬窘境
当以 Batch Size = 1 运行 LLaMA-3 8B（权重大小为 $8 \times 10^9$ 个参数，FP16 占用 $16\text{ GB}$）：
- 每次生成 1 个 Token，总浮点运算量约为：$2 \times 8 \times 10^9 = 1.6 \times 10^{10} \text{ FLOPs}$；
- 必须从 HBM 全量加载权重一次，访存量：$\text{Bytes} \approx 1.6 \times 10^{10} \text{ 字节}$（$16\text{ GB}$）；
- 实际算术强度：
  $$I_{\text{decode}} = \frac{1.6 \times 10^{10} \text{ FLOPs}}{1.6 \times 10^{10} \text{ Bytes}} = 1.0 \text{ FLOP/Byte}$$

### 3. 查看它在屋顶模型上的位置
因为 $1.0 \ll 298.5$，它深深跌落在左侧的访存受限斜坡上！
它所能发挥出的实际硬件算力只有：

$$P = 1.0 \times 3.35 \text{ TB/s} = 3.35 \text{ TFLOPS}$$

实际算力利用率只有：

$$\frac{3.35 \text{ TFLOPS}}{1000 \text{ TFLOPS}} = 0.335\%$$

你没看错，千分之三点三！这就是为什么在单请求推理时，显卡利用率看起来低得吓人。

## 步骤 6：核心系统工程铁律

> **优化代码前，先问屋顶模型：我到底被卡在哪堵墙上？**  
> 如果算术强度 $I < I^*$，优化任何计算指令都是徒劳的，必须全力减少 HBM 访存；只有当 $I > I^*$ 时，优化矩阵乘法、提升并发分块才真正具有物理意义。
