# 第 E02 章：内存物理布局、跨步与合并访存：为什么排整齐能让速度快 10 倍？

同学，你好！在前面两节课里，我们知道了显存带宽是大模型系统中最宝贵的黄金通道。

那么今天这堂课，老师要带你探究一个最基础但又最容易被初学者忽视的工程细节：**我们在内存里摆放数字的姿势**。

你可能会觉得奇怪：“老师，数字不就是存进内存吗？横着摆、竖着摆，计算机不都是按地址去取吗？难道还会影响速度？”  
老师要郑重地告诉你：**不仅会影响，而且速度相差可以高达整整数十倍！**

## 步骤 1：物理直觉（邮递员送信与大巴车接送）

为了让你秒懂，老师打两个生活中的小比方：

### 比方一：邮递员送信
想象你是一位邮递员，今天你的任务是把 32 封信送给同一条街上的 32 户居民：
- **情况 A（排成一排，合并访存）：** 这 32 户人家的门牌号是 1 号、2 号、3 号……连成整齐的一长排。你开着邮车顺着路边缓缓滑行，手一伸，啪啪啪一口气把 32 封信投进并排的邮箱里，**整条街送完只用了 10 秒钟**。
- **情况 B（东一家西一家，跨步非合并访存）：** 32 户人家的地址全被打散了，分别是 1 号、101 号、201 号……分散在城市的 32 个不同街区。每送一封信，你都得在马路上掉头、堵车、等红绿灯、下车投递、再重新启动。同样是送 32 封信，**这一趟下来折腾了你整整半个小时**！

### 比方二：物理芯片的大巴车特性（缓存行 Cache Line）
在 GPU 的物理显存里，有一个极其铁面无私的规则：**它从来不发私家车，只发固定载客 128 人的大客车！**

即使你的程序只需要读取 1 个 2 字节（FP16）的孤单数字，显存总线也绝不会单独为了这 2 个字节跑一趟。它必须一视同仁地从物理显存里**一铲子挖起整整 128 个字节的一整块（这叫一个物理缓存行 Cache Line）**打包送过来。

- 如果一个线程束（Warp）里的 32 个小线程要读的数据刚好紧密挨在一起，那么一辆 128 字节的大巴车开过来，刚好把这 32 个人的数据全部装满运走，**总线利用率 100%**！
- 但如果这 32 个线程各要各的，访问的数据在物理显存里相隔几百米，GPU 就被迫同时派出 32 辆空荡荡的大巴车！每辆大巴车上只孤零零坐了一个 2 字节乘客，其余 126 字节全是空气。**总线有效利用率瞬间暴跌到 1.5%**！

## 步骤 2：芯片微观底层执行机制

在 GPU 芯片内部，最小的基本调度执行单元是由 32 个线程组成的**线程束（Warp）**。

当一个 Warp 里的 32 个线程同时执行一条读取全局显存的指令时，硬件上的内存控制器会立刻对这 32 个线程发出的内存地址进行“安检”：

```
【场景一：合并访存 (Coalesced Memory Access)】
32 个线程请求连续紧邻的物理地址:
Warp 线程:    T0   T1   T2   T3   ...   T30  T31
              │    │    │    │           │    │
目标字节地址: [00] [02] [04] [06]  ...  [60] [62]
              └────┴────┴────┴───────────┴────┘
              ▼
[单次 128 字节物理事务传输完成]  -->  显存总线有效利用率: 100%! (0 浪费)

--------------------------------------------------------------------------------

【场景二：大跨步非合并访存 (Strided Memory Access)】
32 个线程访问离散跳跃的物理地址 (步长 Stride = 128 字节):
Warp 线程:    T0           T1           T2          ...   T31
              │            │            │                 │
目标字节地址: [0000]       [0128]       [0256]       ...  [3968]
              ▼            ▼            ▼                 ▼
          [大巴车 1]    [大巴车 2]    [大巴车 3]          [大巴车 32]
总计触发: 32 次独立的 128 字节物理显存传输事务！
总线实际搬运数据量: 32 x 128 = 4096 字节。
真正有用数据量: 32 个线程 x 2 字节 = 64 字节。
总线传输有效利用率: 64 / 4096 = 1.56%! (98.4% 的宝贵显存带宽全部被浪费在运空气上!)
```

### 多维张量在底层物理内存中的跨步表示（Strides）
在计算机内存里，所有的多维张量（无论你是 2 维矩阵还是 4 维张量）在物理层面上全都是一条**一维扁平的一字长蛇阵**。

那么多维坐标 $(i, j, k)$ 是怎么定位到物理内存位置的呢？老师写出这个经典的定位公式：

$$\text{元素物理偏移量} = \text{base} + i \times \text{stride}_0 + j \times \text{stride}_1 + k \times \text{stride}_2$$

对于一个形状为 $(M, N)$ 的二维矩阵（按行优先存储）：
- `shape` = `(M, N)`
- `stride` = `(N, 1)`
- **横着扫（沿列连续）：** $\text{stride}_1 = 1$，相邻线程拿到的内存地址是相差 1 的连续地址，触发**完美的合并访存**。
- **竖着扫（沿行跨步）：** $\text{stride}_0 = N$，相邻线程拿到的内存地址相差整整 $N$ 个元素。如果 $N=8192$，相邻线程跨越几万字节，访存瞬间变成灾难级的**分散大跨步**！

## 步骤 3：跨组件相互耦合机制

你可能会问：*“老师，我在大模型里什么时候会竖着扫内存呢？”*

老师提醒你注意两个大模型中最常见的隐形性能陷阱：

1. **注意力机制中的转置陷阱（$Q K^\top$）：**  
   在计算注意力时，我们需要把 Key 向量进行转置。在 PyTorch 中写一句 `K.transpose(-1, -2)` 只耗费 0 微秒，因为它根本没搬运任何数据，只是把 `stride` 元组调换了一下。  
   但是！当接下来的矩阵乘法读取这个转置后的矩阵时，由于内层跨步不再是 1，相邻线程全部在做大跨步非合并读取！如果不做片上转置平铺优化，显存读取带宽就会被平白无故丢掉 70% 以上。
2. **LoRA 微调与量化反量化：**  
   低秩适应（LoRA）引入了小型旁路矩阵 $A$ 和 $B$。如果这两个矩阵的内存跨步没有与主模型的权重严格对齐，合并访存机制就会被打破，原本旨在加速的微调算子反而会因为内存访问碎片化而变慢。

## 步骤 4：精确性能数学公式

设一个线程束中 32 个线程请求的地址跨度为 $S$（单位为字节）。硬件每次传输的物理事务块大小为 $B_{\text{trans}} = 128 \text{ 字节}$，每个线程请求的数据有效字节为 $b_{\text{elem}}$（如 FP16 下 $b_{\text{elem}} = 2$）。

合并访存所需的物理总线事务次数为：

$$N_{\text{transactions}} = \left\lceil \frac{\max(\text{Addr}) - \min(\text{Addr}) + b_{\text{elem}}}{B_{\text{trans}}} \right\rceil$$

总线有效利用率（Bus Efficiency）定义为：

$$\eta_{\text{bus}} = \frac{32 \times b_{\text{elem}}}{N_{\text{transactions}} \times B_{\text{trans}}}$$

当地址严格连续且对齐时：
$$N_{\text{transactions}} = 1 \implies \eta_{\text{bus}} = \frac{32 \times 2}{1 \times 128} = \frac{64}{128} = 50\% \quad (\text{单次 64B/128B 事务完全对齐时可达 } 100\%)$$

当跨步大于 128 字节时：
$$N_{\text{transactions}} = 32 \implies \eta_{\text{bus}} = \frac{64}{32 \times 128} = \frac{64}{4096} \approx 1.56\%$$

## 步骤 5：具体微基准数字推导

我们来做一次实测模拟推导！

假设在 LLaMA-3 70B 模型中，对一个形状为 $(4096, 8192)$ 的权重激活矩阵执行逐元素处理，数据格式为 FP16（每个元素 2 字节）：
- 总元素数：$4096 \times 8192 = 33,554,432$ 个元素
- 理论有效数据量：$33,554,432 \times 2 \approx 67.1 \text{ MB}$

### 1. 合并访存场景（按行遍历，连续读取）
- 触发物理传输事务数：
  $$\frac{67.1 \times 10^6 \text{ 字节}}{128 \text{ 字节/事务}} \approx 524,288 \text{ 次事务}$$
- 在 H100（$3.35\text{ TB/s}$）上的纯搬运耗时：
  $$T_{\text{coalesced}} = \frac{67.1 \times 10^6}{3.35 \times 10^{12}} \approx 20.0 \;\mu\text{s}$$

### 2. 严重跨步非合并访存场景（错误地按列跨步遍历，跨步为 8192 元素）
- 每个线程读取的数据落在完全不同的 128 字节缓存行中！
- 实际被迫发起的物理事务总数据量：
  $$33,554,432 \times 128 \text{ 字节} \approx 4.29 \text{ GB}!$$
- 耗时暴涨为：
  $$T_{\text{strided}} = \frac{4.29 \times 10^9}{3.35 \times 10^{12}} \approx 1280.0 \;\mu\text{s} = 1.28 \text{ ms}$$
- **性能差距：** $1280 \;\mu\text{s} \div 20 \;\mu\text{s} = 64 \times$！  
  仅仅因为换了一个循环遍历方向，耗时整整慢了 **64 倍**！

## 步骤 6：核心系统工程铁律

> **让相邻的线程在相邻的物理内存上并肩作战。**  
> 永远保证内层计算循环沿着张量跨步为 1 的最内层连续维度展开；任何打破内存对齐与连续性的操作，都必须在片上高速缓存中完成转置重排，绝不让碎片化的大跨步访存践踏宝贵的高带宽显存。
