# 第 E02 章：内存物理布局、跨步与合并访存：DRAM 突发传输与张量跨步

## 步骤 1：物理直觉

想象你是一位邮递员，今天要给枫树街上门牌号为 1 到 32 号的 32 户人家派送信件：

- **合并访存场景（Coalesced）：** 1 到 32 号人家紧密挨在一起，连成一排。你开着邮车顺着街道平缓驶过，一次性把 32 封信按顺序塞进并排的邮箱里，整条街派送只需 10 秒钟。
- **跨步非合并访存场景（Strided / Uncoalesced）：** 32 户人家的地址被错误地按照 32 的跨步打印（分别是 1 号、33 号、65 号、97 号，分散在整座城市的各个远郊角落）。每送出一封信，你都必须驱车穿越几个街区、重新倒车停车、下车投递、再重新起步。同样派发 32 封信，现在却需要耗费整整半小时！

在 GPU 硅基芯片底层，高带宽显存（HBM）从来不会单独抓取一个 2 字节（FP16）的单独数字。无论线程向硬件请求读取多少字节，**底层的物理 DRAM 总线控制器每次都会执行一次固定大小为 32 字节或 128 字节的宽总线块抓取（物理缓存行 Cache Line）**。

如果一个线程束（Warp）内的 32 个线程请求的是连续相邻的物理显存地址，这 32 个独立的数据请求就会瞬间被硬件**合并（Coalesce）**成一到两次干净利落的 128 字节缓存行传输（总线利用率 $100\%$）。但如果线程以大跨步访问分散的显存地址，GPU 将被迫发起多达 32 次独立的 128 字节物理事务去抓取仅仅 64 字节的有效数据，导致总线效率暴跌至 **$1.5\%$**！

## 步骤 2：芯片微观底层执行机制

GPU 芯片内部以 32 个并发线程构成的**线程束（Warp）**为基础执行单元。当一个 Warp 中的 32 个线程同时执行一条全局显存读取指令（例如 `LDG.E`）时，硬件内存管理单元（MMU）会立即扫描这 32 个线程所请求的目标物理显存地址：

```
合并访存场景 (连续内存地址):
Warp 线程:    T0   T1   T2   T3   ...   T30  T31
              │    │    │    │           │    │
目标字节地址: [00] [02] [04] [06]  ...  [60] [62]
              └────┴────┴────┴───────────┴────┘
              ▼
[单次 128 字节 HBM DRAM 突发传输完成]  -->  总线有效利用率: 100% (0 浪费字节)

非合并 / 大跨步访存场景 (跨步 Stride = 128 字节):
Warp 线程:    T0           T1           T2          ...   T31
              │            │            │                 │
目标字节地址: [0000]       [0128]       [0256]       ...  [3968]
              ▼            ▼            ▼                 ▼
            [128B]       [128B]       [128B]             [128B]
总计触发: 32 次独立的 128 字节 HBM 传输事务 = 总线共传输了 4096 字节!
实际有用数据: 32 个线程 x 2 字节 = 64 字节。
总线传输有效率: 64 / 4096 = 1.56% (高达 98.4% 的显存带宽被彻底浪费在路上!)
```

### 多维张量在底层物理内存中的跨步表示（Strides）
在 PyTorch 与 C++ 底层，任何高维张量在物理介质上都是一块一维扁平连续排布的物理字节数组，其多维寻址依靠 `shape`（形状）与 `stride`（跨步）元组确定：

$$\text{元素物理偏移量}(\mathbf{x}_{i, j, k}) = \text{base\_ptr} + i \times \text{stride}_0 + j \times \text{stride}_1 + k \times \text{stride}_2$$

对于一个形状为 $(M, N)$、以**行优先（Row-Major / C-contiguous）**格式存储的二维张量：
- `shape` = `(M, N)`
- `stride` = `(N, 1)`
- 沿着列坐标 $j$ 连续遍历时，$\text{stride}_1 = 1$，相邻线程访问的是紧挨着的物理内存，实现完美的**合并访存**。
- 沿着行坐标 $i$ 连续遍历时，$\text{stride}_0 = N$，相邻线程访问的内存地址在物理上间隔了 $N$ 个元素。如果 $N$ 很大，访存就会蜕化为完全分散的**跨步非合并访存**！

## 步骤 3：跨组件相互耦合机制

物理显存排布方式，直接决定了多个 LLM 核心模块的实际吞吐：

1. **注意力机制中的转置隐形惩罚（$Q K^\top$）：**  
   在标准多头注意力中，为了计算 Query $\mathbf{Q} \in \mathbb{R}^{B \times H \times S \times d}$ 与 Key $\mathbf{K} \in \mathbb{R}^{B \times H \times S \times d}$ 的点积，必须将 $\mathbf{K}$ 的后两个维度转置为 $(B, H, d, S)$。  
   在 PyTorch 中调用 `K.transpose(-1, -2)` 本身不会产生任何数据搬运，它仅仅是将底层的跨步元组由 `(d, 1)` 修改为 `(1, d)`。  
   当后续的 GEMM 算子读取这个转置后的 $\mathbf{K}$ 时，连续线程在读取同一个特征维度时，地址跨度变成了 $d$ 个元素。如果单头维度 $d = 128$（在 FP16 下对应 256 字节），由于跨度大于 128 字节，相邻线程的请求无法合并，若无片上 SRAM 转置缓冲区，多达 $75\%$ 的显存读取带宽将被白白丢弃。

2. **自回归解码阶段的 KV Cache 布局抉择：**  
   在逐字生成阶段，KV Cache 的维度排序主要有两种方案：
   - 布局 A：`[batch, num_heads, max_seq_len, head_dim]`
   - 布局 B：`[max_seq_len, batch, num_heads, head_dim]`
   在布局 A 下，随着序列长度推进，读取单个请求的历史上下文时，在最内层的 `head_dim` 维度上是完全连续的（$\text{stride} = 1$），线程束可以达到 100% 的合并访存效率。

3. **隐蔽的 `.contiguous()` 显存带宽消耗：**  
   当某些特定算子（如部分老旧 CUDA 库）强制要求输入张量必须在内存中严格连续时，工程师往往会在代码中添加 `.contiguous()`。  
   调用 `.contiguous()` 会在后台默默启动一个显式的数据深拷贝 CUDA 算子，完整遍历非连续显存并向 HBM 写入一份全新的连续数组。对于 70B 模型而言，一次不必要的 `.contiguous()` 就会吞噬数十吉字节的 HBM 带宽，导致数毫秒的显卡停顿。

## 步骤 4：精确性能数学公式

显存合并访问效率 $\eta_{\text{coalesce}}$ 定义为：

$$\eta_{\text{coalesce}} = \frac{\text{线程束请求的实际有效数据字节数}}{\text{底层硬件实际触发的缓存行总数} \times L_{\text{line}}}$$

其中 $L_{\text{line}}$ 为硬件物理内存事务的最小粒度（L1/SRAM 中通常为 $32\text{ 字节}$，L2/HBM 突发通常为 $128\text{ 字节}$）。

一个 Warp 包含 32 个线程，处理 FP16 数据（每线程 2 字节）时，有效数据需求为：

$$\text{有效字节数} = 32 \times 2 = 64 \text{ 字节}$$

- 若实现**完全合并**（32 个线程的地址全都落在同一个对齐的 128 字节物理区间内）：
  $$\eta_{\text{coalesce}} = \frac{64}{1 \times 128} = 50\% \quad (\text{在支持 32 字节细粒度扇区的架构下可达 } 100\%)$$
- 若**完全分散**（跨步跨度大于 64 个元素，即 $\ge 128\text{ 字节}$），每个线程都落在不同的缓存行内：
  $$\eta_{\text{coalesce}} = \frac{64}{32 \times 128} = \frac{64}{4096} \approx 1.56\%$$

由此，算子所能体验到的**有效物理显存带宽** $\text{BW}_{\text{eff}}$ 为：

$$\text{BW}_{\text{eff}} = \eta_{\text{coalesce}} \times \text{BW}_{\text{peak}}$$

在峰值带宽为 $3.35\text{ TB/s}$ 的 H100 SXM 上，如果算子访存未合并（$\eta = 1.56\%$），其实际可用带宽将急剧缩水至：

$$\text{BW}_{\text{eff}} = 0.0156 \times 3350 \text{ GB/s} \approx 52.3 \text{ GB/s}$$

**这直接把价值数十万元的先进 HBM3 显存，硬生生拉低成了普通家用笔记本内存（DDR5）的龟速！**

## 步骤 5：具体微基准数字推导

我们来手算一段真实场景：一个 Warp 内的 32 个线程从行优先存储的 Key 张量中读取数据：
- 张量形状：序列长度 $S = 4096$，单头维度 $d = 128$
- 数据格式：FP16（每元素 2 字节）
- 内存排布：行优先存储，行跨步 $\text{stride}_0 = 128 \times 2 = 256\text{ 字节}$，列跨步 $\text{stride}_1 = 2\text{ 字节}$。

### 场景 A：行向读取（遍历维度，列跨步为 1）
- 线程 $k$（$k \in [0, 31]$）读取第 $i$ 个 Token 向量的第 $k$ 个维度分量：
$$\text{物理地址}(k) = \text{base} + i \times 256 + k \times 2$$
32 个线程请求的地址范围为从偏移量 $0$ 到 $62$ 字节。
- 这 32 个地址全部落在**单次 128 字节 DRAM 传输区间**（0 至 127 字节）之内。
- DRAM 实际传输量：$128\text{ 字节}$。
- 有用数据量：$64\text{ 字节}$。
- **总线利用率：$50\%$**（在 32 字节扇区架构下为 $100\%$）。

### 场景 B：列向读取（沿时间步读取同一个特征分量，行跨步为 256）
- 线程 $k$（$k \in [0, 31]$）在固定特征维度 $j$ 上，读取连续 32 个时间步的 Token：
$$\text{物理地址}(k) = \text{base} + k \times 256 + j \times 2$$
- 线程 0 请求地址偏移：$0$。
- 线程 1 请求地址偏移：$256$。
- 线程 2 请求地址偏移：$512$。
- ...
- 线程 31 请求地址偏移：$7936$。

注意：相邻两个线程请求的地址间隔了整整 $256\text{ 字节}$。因为硬件单次缓存行大小只有 $128\text{ 字节}$，**没有任何两个线程能共享同一个缓存行！**
- 显存控制器必须发起 **32 次完全独立的 128 字节突发传输**。
- DRAM 实际从显存搬运的总量：$32 \times 128 = 4096\text{ 字节}$。
- 真正送给线程运算的有用数据量：$32 \times 2 = 64\text{ 字节}$。
- **总线利用率：$\frac{64}{4096} = 1.56\%$**。
- **耗时差距：场景 B 的物理读取耗时是场景 A 的整整 32 倍！**仅仅是因为内存访问方向与底层物理布局垂直。

## 步骤 6：核心系统工程铁律

> 张量维度不是抽象的数学坐标，而是具体的物理内存指针。在高性能大模型工程实现中，非连续跨步访问会导致高达 98% 的显存带宽在传输途中被白白废弃。永远确保线程束中最快变化的线程索引（ThreadIdx.x），严格对齐在物理显存最内层的连续维度（Stride = 1）之上。
