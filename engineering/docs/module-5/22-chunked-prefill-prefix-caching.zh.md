# 第 E22 章：分块预填与前缀缓存技术：长提示词切片调度以平抑 ITL 抖动，利用 Radix Tree 实现前缀零开销复用

## 步骤 1：物理直觉

想象一家繁忙的快餐汉堡店：
- **前缀缓存（Prefix Caching）：** 很多顾客点单的第一句话都是一模一样的：“我要一份招牌牛肉堡套餐，加冰可乐”（重复的长系统提示词 System Prompt）。聪明的店长绝不会每次都从头杀牛榨油，而是把做好的 50 份半成品汉堡胚恒温保温在架子上（**前缀缓存**）。新顾客一开口，店员一秒钟取出半成品，只需最后往上面挤一滴特调沙拉酱即可出餐！
- **分块预填（Chunked Prefill）：** 突然，一位顾客进门要为全公司订购 500 个汉堡（一个长达 32K Token 的超长提示词）。如果厨房把所有员工全部调去立刻做这 500 个汉堡，外面所有排队买单杯咖啡的散客都会被晾在原地 20 分钟（严重破坏逐字交互延迟 ITL）。店长规定：每次只做 50 个汉堡（**切片分块 Chunking**），做完 50 个就回头帮散客打一杯咖啡，然后再做 50 个。这样，既做完了大单，散客的体验也丝毫不受影响！

## 步骤 2：芯片微观底层执行机制

### 1. 前缀缓存（Prefix Caching）与基数树（Radix Tree）
在多轮对话或复杂 Agent 场景中，大量请求共享相同的 System Prompt、Few-Shot 示例或检索增强上下文（RAG Context）：
- 传统推理：每次请求到来，即使前 3000 字一模一样，GPU 也必须从头执行一次完整的 Prefill，并把 KV Cache 重新算一遍；
- **Radix Tree 缓存机制（如 SGLang / vLLM）：** 在内存中用树状结构索引 Token 序列。新请求到达时，系统在 Radix Tree 中秒级检索匹配最长公共前缀；命中的历史物理 Block 被直接重用并加锁，**完全免除了对应前缀的全部浮点计算与显存写入**，首字延迟（TTFT）暴降为微秒级！

```
Radix Tree 前缀缓存结构:
[系统提示词 System Prompt: "You are a helpful assistant..."] (物理块 0 ~ 15)
                             │
            ┌────────────────┴────────────────┐
            ▼                                 ▼
   [知识库文档 A: "RAG Doc 1..."]    [知识库文档 B: "RAG Doc 2..."]
   (物理块 16 ~ 31)                  (物理块 32 ~ 47)
            │                                 │
            ▼                                 ▼
      [用户提问 1]                      [用户提问 2]
```

### 2. 分块预填（Chunked Prefill，如 Sarathi-Serve）
将长度极长的提示词输入切割成固定大小的块（例如每个 Chunk 包含 512 个 Token）：
- 在每次推理调度时，将“一个 512 大小的 Prefill 切片”与“正在生成的若干个 Decode 请求”**混合打包成同一个 Batch 执行**；
- 使得该 Batch 的算术强度刚好达到硬件平衡点，既充分榨干了 Tensor Core 算力，又彻底避免了巨型 Prefill 霸占 GPU 导致的自回归打字停顿。

## 步骤 3：跨组件相互耦合机制

1. **ITL（逐字延迟）方差的大幅抹平：**  
   未采用 Chunked Prefill 前，系统的 ITL 监控曲线上布满刺眼的高尖刺脉冲（每当有长提示词涌入就卡顿数百毫秒）；引入切片后，ITL 曲线平稳得像一条直线，SLA 保证率达到 99.9%。
2. **写时复制与 LRU 缓存驱逐：**  
   前缀缓存池使用引用计数与 LRU 机制管理。当显存紧张时，自动释放最久未被访问的公共前缀物理块，保证活跃服务的高可用。

## 步骤 4：精确性能数学公式

对于共享前缀长度为 $S_{\text{prefix}}$、新输入长度为 $S_{\text{new}}$ 的请求：

### 传统首字延迟（TTFT）：
$$\text{TTFT}_{\text{standard}} = \frac{2 \cdot P \cdot (S_{\text{prefix}} + S_{\text{new}})}{P_{\text{compute}}} + T_{\text{attn}}(S_{\text{prefix}} + S_{\text{new}})$$

### 前缀缓存命中时的首字延迟：
$$\text{TTFT}_{\text{cached}} = \frac{2 \cdot P \cdot S_{\text{new}}}{P_{\text{compute}}} + T_{\text{attn\_append}}(S_{\text{prefix}}, S_{\text{new}})$$

首字延迟缩短比例：

$$\Delta \text{TTFT} \approx \frac{S_{\text{prefix}}}{S_{\text{prefix}} + S_{\text{new}}}$$

当处理长 RAG 文档（如 $S_{\text{prefix}} = 8000$，新提问 $S_{\text{new}} = 100$）时：

$$\Delta \text{TTFT} \approx \frac{8000}{8100} \approx 98.7\% \text{ 的首字延迟被彻底消灭！}$$

## 步骤 5：具体微基准数字推导

以企业级 Agent 助手部署为例，系统预置了 $4096$ 个 Token 的长规则提示词，用户连续发起多轮追问：
- 模型：LLaMA-3 70B（H100 SXM，前向预填速度约 4000 Tokens/秒）

### 场景 A：无前缀缓存
每轮追问到来，GPU 都必须重新解析这 4096 个词的系统提示词：
- 每次额外计算耗时：$T = \frac{4096}{4000} \approx 1.02 \text{ 秒}$。
- 用户发送一条短消息，必须在屏幕前死等 **1 秒多** 才能看到第一个字出现！

### 场景 B：采用 Radix Tree 前缀缓存
这 4096 个 Token 的 KV Cache 早已保存在物理显存池中：
- 计算耗时：仅为用户当次提问的 20 个词，耗时不足 $0.005\text{ 秒}$（$5\text{ ms}$）！
- **首字延迟从 $1020\text{ ms}$ 断崖式下跌至 $5\text{ ms}$（提速超 200 倍！）**，用户体验达到丝滑的即时响应。

## 步骤 6：核心系统工程铁律

> 生产环境中最昂贵的算力浪费，是对完全相同的上下文进行无休止的重复计算。通过 Radix Tree 将历史 KV Cache 沉淀为可重用的物理数据资产，并用 Chunked 切片平抑长输入冲击，是构建现代化低延迟长文本推理服务的双子灯塔。
